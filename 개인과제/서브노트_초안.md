# Chapter 1. 고객 중심 서비스 이해

## 1. 서비스 개요

> 💡 템플릿 원본은 "FastAPI + MariaDB 경량 To-do"였습니다. 우리 것으로 바꿔 씁니다.
> 반드시 들어가야 할 3가지: (1) 무엇을 하는 시스템인지 (2) 몇 개 서비스로 쪼개져 있는지 (3) 왜 쪼갰는지

본 프로젝트는 Spring Boot 기반 마이크로서비스 7종과 FastAPI 기반 추천 서비스 1종,
그리고 Kafka·MariaDB로 구성된 **온라인 강의 수강신청 플랫폼**입니다.
회원가입·강의조회·수강신청·결제·추천이라는 하나의 사용자 여정을 **독립 배포 가능한 서비스 단위로 분리**하여,
특정 기능의 부하나 장애가 전체 서비스로 번지지 않도록 설계되어 있습니다.

# Chapter 2. 시스템 기술 구조 및 설계 이유

## 1. 모놀리식이 아니라 MSA인 이유

> 💡 원본 템플릿의 "REST API 등장 배경"을 대체하는 절입니다.
> 교재 논리(역할 분리 → 유연한 확장)를 MSA 층위로 한 단계 올려 쓰면 됩니다.

기존 모놀리식은 화면·비즈니스 로직·데이터가 한 덩어리라, 한 기능의 장애나 부하가 전체를 멈춥니다.
본 시스템은 이를 **기능 단위 서비스로 분리**하고, 서비스 간에는 REST(동기)와 Kafka(비동기)를 목적에 따라 나눠 씁니다.
→ 이 주장의 실제 증거는 §5(서비스 독립성 실험)에 있습니다.

## 2. 서비스 구성과 기술 선택 이유

> 💡 원본은 "왜 FastAPI인가" 한 절이었지만, 우리는 8개 중 7개가 Spring입니다.
> 질문을 **"왜 추천 서비스만 FastAPI인가"** 로 바꾸는 게 정확합니다.
> 📸 스크린샷 ① Eureka 대시보드 (등록된 서비스 목록)

| 구성요소 | 포트 | 역할 | 기술 | 내가 수정하나 |
|---|---|---|---|---|
| api-gateway | 8080 | 단일 진입점, 라우팅·인증 필터 | Spring Cloud Gateway | ✕ 인프라 |
| eureka-server | 8761 | 서비스 디스커버리(주소록) | Spring Cloud Netflix | ✕ 인프라 |
| auth-server | 9000 | 로그인·토큰 발급 | Spring Authorization Server | ✕ 인프라 |
| user-service | 8081 | 회원가입·로그인·조회 | Spring Boot | △ |
| course-service | 8082 | 상품(과목) 등록·조회·검색 | Spring Boot | ○ |
| enrollment-service | 8083 | 신청·상태 관리 (Kafka 송수신) | Spring Boot | ○ |
| payment-service | 8084 | 결제 처리 (Kafka 발행) | Spring Boot | ○ |
| recommend-service | 8085 | 규칙 기반 추천 | **FastAPI** | ○ |
| kafka | 9092 | 서비스 간 비동기 이벤트 통로 | Kafka | ✕ |
| mariadb | 3306→3379 | 데이터 저장 (테이블 단위 분리) | MariaDB | ✕ |

**추천 서비스만 FastAPI인 이유 (4가지)**
1. **Python ML 생태계와 직결** — 추천 로직은 향후 협업 필터링·모델 서빙으로 확장될 영역이라, 대부분의 ML 프레임워크가 있는 Python이 유리합니다.
2. **비동기 처리** — Starlette 기반으로 다수의 조회 요청을 효율적으로 처리합니다. 실제로 `main.py`의 `lifespan`에서 Kafka Consumer와 Eureka 등록을 async로 띄웁니다.
3. **자동 문서화(`/docs`)** — 별도 작업 없이 Swagger UI가 생성되어 실습·협업에서 바로 테스트 가능합니다.
4. **Pydantic 유효성 검증** — `app/model/schemas.py`에서 요청/응답 구조를 타입으로 고정합니다.

> 💡 여기 "폴리글랏(polyglot) 아키텍처" 한 단어를 쓰면 좋습니다.
> 서비스가 분리돼 있으니 **서비스마다 다른 언어/프레임워크를 쓸 수 있다**는 것 자체가 MSA의 장점입니다.

### 3-2. 서비스 내부 구조 (recommend-service 실제 트리)

> 💡 원본 템플릿의 `main.py / routers / cruds / models / schemas / database.py` 트리에 대응하는 부분입니다.
> 우리 코드는 계층이 조금 더 나뉘어 있습니다 (client, kafka가 추가).

```
recommend-service/
├── main.py                        → 앱 진입점. lifespan에서 Eureka 등록 + Kafka Consumer 기동
├── app/
│   ├── router/recommend_router.py → URL별 API 엔드포인트 정의
│   ├── service/recommend_service.py → 추천 규칙(비즈니스 로직) — ★ 우리가 고칠 파일
│   ├── client/course_client.py     → course-service 호출 (서비스 간 REST)
│   ├── client/enrollment_client.py → enrollment-service 호출
│   ├── kafka/consumer.py           → enrollment 이벤트 수신 (비동기)
│   ├── model/schemas.py            → 요청/응답 데이터 구조 (Pydantic)
│   └── config/settings.py, security.py → 환경설정, 토큰 검증
├── Dockerfile
└── requirements.txt
```

**요청 처리 흐름**
```
클라이언트가 URL로 요청
  → router 에서 해당 경로 함수 실행
  → schemas 로 요청 데이터 자동 파싱 및 유효성 검증
  → service 에서 추천 규칙 실행
      └ 필요한 데이터는 client 를 통해 다른 서비스에 REST 호출
  → 결과를 다시 schemas 로 포맷팅하여 응답
```

> 💡 **원본 템플릿과 결정적으로 다른 점을 한 줄 쓰세요.**
> 단일 앱은 `cruds`가 자기 DB를 직접 읽지만, 우리 추천 서비스는 **`client`를 통해 다른 서비스에 물어봅니다.**
> 이게 "DB를 공유하지 않는다"는 MSA 원칙의 실제 코드 상 모습입니다.

## 5. 동기(REST) vs 비동기(Kafka) — 어디서 왜 나뉘는가

> 💡 Phase 4 결과표. **이 절이 없으면 "MSA를 이해했다"고 인정받기 어렵습니다.**

| 구간 | 방식 | 왜 이 방식인가 |
|---|---|---|
| 프론트 → 게이트웨이 → 각 서비스 | REST | 사용자가 화면에서 **즉시 응답**을 기다림 |
| recommend → course/enrollment | REST | 추천 계산에 그 데이터가 **당장 필요** |
| payment → enrollment (`payment.completed`) | Kafka | 결제 완료를 알리기만 하면 됨. **결제가 수강 상태 변경을 기다릴 이유가 없음** |
| enrollment → recommend (`enrollment.completed`) | Kafka | 추천 갱신은 **늦어도 되는 작업** |

> 교재 p33 요지: 즉시 응답이 필요하면 REST, 느슨한 결합·이벤트 전파가 목적이면 Kafka.

## 1. 컨테이너가 일부만 뜬다

- ❌ 증상: `up -d` 했는데 `docker ps`에 4개만 보임
- 🤔 처음 추측: 이미지 빌드가 실패한 줄 알았음
- 🔍 실제 원인: `depends_on: condition: service_healthy` 로 auth-server가 healthy 될 때까지(최대 120초) 뒤 서비스들이 대기
- ✅ 해결: 3분 기다린 후 재확인
- 💡 배운 것: compose의 `depends_on`은 **줄을 세우는 것**이지 실패가 아니다

## 2. 포트 충돌

- ❌ 증상: `port is already allocated`
- 🔍 실제 원인: 이전 실습 컨테이너가 8080·3000을 점유 중
- ✅ 해결: `docker stop spring-backend frontend vue-frontend fastapi-backend`
- 💡 배운 것: 컨테이너는 여러 개여도 **호스트 포트는 하나뿐**이다

## 3. 화면은 뜨는데 목록이 0건

- ❌ 증상: 강의 목록이 비어 있음. 에러는 안 남
- 🔍 실제 원인: `./init-db` 폴더가 없어 Docker가 **빈 폴더를 자동 생성**해 마운트
- ✅ 해결: init-db/01_init.sql 존재 확인 후 `down -v` → `up -d`
- 💡 배운 것: **에러가 안 나는 실패**가 가장 찾기 어렵다

## 4. 시드 SQL을 고쳤는데 반영이 안 됨

- ❌ 증상: `01_init.sql`을 수정하고 재기동해도 예전 데이터
- 🤔 처음 추측: SQL 오타인 줄 알았음
- 🔍 실제 원인: `down`만 해서 MariaDB **볼륨이 남아 있었음**
- ✅ 해결: `docker compose down -v` 후 재기동
- 💡 배운 것: MariaDB 초기화 스크립트는 **데이터 디렉터리가 비어 있을 때만** 실행된다

## 5. 게이트웨이(8080) 호출 시 401

- ❌ 증상: 토큰을 넣었는데도 401
- 🤔 처음 추측: 내 토큰이 잘못된 줄 알았음
- 🔍 실제 원인: compose에서 gateway·recommend의 issuer는 `http://localhost:8080`, user·course·enrollment·payment는 `http://auth-server:9000` 으로 **서로 다름**
- ✅ 해결: 개별 서비스 포트로 우회 호출 / 강사 확인
- 💡 배운 것: **내 실수가 아니라 설정 문제일 수도 있다**. 분산 시스템은 설정 불일치가 곧 장애다

## 6. 컨테이너 안에 들어가려는데 bash가 없음

- ❌ 증상: `docker exec -it ... bash` → `executable file not found`
- 🔍 실제 원인: 경량 베이스 이미지에는 bash가 없음
- ✅ 해결: `docker exec -it <container> sh`
- 💡 배운 것: 이미지 경량화의 대가는 **디버깅 도구의 부재**다
