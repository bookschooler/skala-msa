백엔드는 PPT와 정확히 일치합니다.
그런데 프론트엔드가 그 흐름을 쓰지 않습니다.

PENDING → Kafka → ACTIVE 전환은 서버에서 실제로 일어납니다. 하지만 「내 신청내역」 화면은 서버를 조회하지 않고 브라우저 localStorage를 읽습니다. 그래서 슬라이드 12가 약속한 시연 장면 — 접수 처리 중에서 접수 완료로 바뀌는 순간 — 이 현재 상태로는 재현되지 않습니다.

03

어긋나는 항목

번호는 심각도 순이 아니라 채팅에서 공유한 순서 그대로입니다. 발표 기준 우선순위는 마지막 절에 정리했습니다.

1
시연 차단

「내 신청내역」이 서버가 아니라 브라우저 저장소를 읽습니다

getMine() (= GET /api/enrollments/my) 은 정의만 되어 있고 호출하는 곳이 한 군데도 없습니다. 신청 직후 로컬에 status: 'RECEIVED' 를 바로 기록하기 때문에 화면은 처음부터 「접수완료」입니다. 슬라이드 12의 “After 1 접수 처리 중” 장면을 만들 수 없습니다.

GET /api/enrollments/my 를 실제로 호출하는 파일은 구버전 EnrollmentView.vue 인데, 라우터가 /enrollments 를 /applications 로 리다이렉트해서 접근 자체가 불가능합니다. 추가로 액세스 토큰이 demo-token 이면 POST조차 보내지 않습니다.

  • api/application.js:5 — getMine() 정의, 사용처 0
  • store/application.js:47 — demo-token이면 서버 호출 생략
  • store/application.js:54 — status: 'RECEIVED' 로컬 하드코딩
  • views/MyApplicationsView.vue:48 — applicationStore(localStorage)만 참조
  • router/index.js — /enrollments → /applications 리다이렉트

ACTIVE → GET /api/enrollments/my 로 접수 완료 확인
코드가 하는 것

3
높음

화면에 「신청취소」 버튼이 있는데 취소 API가 없습니다

프론트는 DELETE /api/enrollments/{id} 를 호출하려 하지만 EnrollmentController 에 DELETE 매핑이 없습니다. 다만 지금은 로컬 ID가 AP-2026-xxxxxx 문자열이라 typeof target.id === 'number' 조건에 걸리지 않아 호출 자체가 일어나지 않습니다. 결과적으로 화면에서만 취소되고 서버 DB에는 신청이 그대로 남습니다.

  • api/application.js — cancel() → DELETE /api/enrollments/{id}
  • store/application.js:72 — 숫자 ID일 때만 호출 (실제로는 문자열)
  • EnrollmentController.java — DELETE 매핑 없음
  • MyApplicationsView.vue:28 — 「신청취소」 버튼 노출

중간

보완 기회

다이어그램에 빠진 실제 흐름이 두 개 있습니다

둘 다 코드에 이미 구현되어 있는데 슬라이드 8에는 없습니다. 없어서 틀린 게 아니라, 넣으면 이벤트 기반 설계를 더 잘 보여줄 수 있는 쪽입니다. 슬라이드 9의 Kafka 설명도 「신청 상태 갱신」만 적혀 있어 함께 보완할 수 있습니다.

  • Enrollment → Kafka → Recommend — enrollment.completed 발행 및 소비
  • EnrollmentKafkaProducer.java · recommend-service/app/kafka/consumer.py
  • Enrollment → Course — POST /internal/{id}/enrollment-count (신청자 수 증가)
7
시연 리스크

접수 처리가 한 번 실패하면 그 계정은 해당 공고에 영구히 다시 신청할 수 없습니다

PENDING 레코드는 REQUIRES_NEW 로 먼저 커밋됩니다. 이후 Payment 호출이 실패하면 응답은 500이지만 PENDING은 DB에 남습니다. 중복 검사가 상태를 가리지 않고 (user_id, course_id) 조합만 보기 때문에, 재신청은 “이미 신청함” 으로 막힙니다.

시연 중 Kafka나 Payment가 한 번 삐끗하면 DB를 직접 건드리지 않고는 복구할 수 없습니다. 발표 직전 시연 계정을 리셋해 두는 것으로도 당장은 대응됩니다.

  • EnrollmentWriteService.java — Propagation.REQUIRES_NEW
  • EnrollmentService.java:42 — existsByUserIdAndCourseId (상태 무관)
  • init-db/01_init.sql — enrollments UNIQUE (user_id, course_id)
8
미완성

슬라이드 11 「대표 Request / Response」가 아직 빈 페이지입니다

제목만 있고 내용이 없습니다. 실제 요청·응답 예시는 코드에서 그대로 뽑아낼 수 있습니다.

04

발표 전 처리 순서

1번 하나만 고치면 PPT 내용이 사실이 됩니다. 나머지는 발표 완성도 문제입니다.

「내 신청내역」을 서버 응답으로 갈아끼우기

MyApplicationsView 가 GET /api/enrollments/my 를 호출하고, PENDING 은 「접수 처리 중」, ACTIVE 는 「접수완료」로 표시하게 합니다. 2번 상태 매핑이 여기서 함께 해결되고, 슬라이드 12 시연 시나리오가 그대로 재현됩니다.

사용자에게 보이는 문구에서 강의 용어 걷어내기
