```

  course-service ──WebClient──→ enrollment-service
    (청약 신청 시 단지 정보 검증: GET /api/courses/{id})

  enrollment-service ──WebClient(동기)──→ payment-service
    (결제 요청: PaymentServiceClient)

  payment-service ──[Kafka: payment.completed]──→ enrollment-service
    (결제 완료 → PENDING → ACTIVE 상태 변경)

  enrollment-service ──[Kafka: enrollment.completed]──→ recommend-service
    (청약 완료 후 추천 갱신 트리거)

[Phase C — 13:00~15:00: 프론트 연결 + PPT 취합]

  PPT 각 파트 초안 → #1이 취합

[Phase D — 15:00~ 발표 전: E2E 테스트]
  docker compose up -d (약 3~5분 소요)
  최소 목표: 청약 신청 → Kafka 이벤트 → 추천 반영 1개 플로우 완주
  전체 시나리오: 목록 조회 → 단지 상세 → 청약 신청 → 내역 확인 → AI 추천
  B2G2C 증명: Swagger GET /api/courses → 청약홈+LH 두 기관 통합 데이터 확인
```

### PPT 필수 포함 내용 (텍스트북 평가 기준)

#### Agile (슬라이드 4)
- 스프린트 **계획 → 실행 → 회고** 3단계 사이클 명시
- Sprint 1 백로그 & 완성 결과 비교 표

#### MSA 3가지 핵심 패턴 (슬라이드 10·14)
| 패턴 | 우리 프로젝트에서 | 설명할 것 |
|------|----------------|---------|
| **Eureka** | 모든 서비스 등록, 서비스명으로 상호 검색 | 왜 IP 하드코딩 대신 이걸 쓰는지 |
| **Kafka** | payment→enrollment 상태변경, enrollment→recommend 갱신 | 동기 방식 대비 왜 비동기인지 |
| **API Gateway** | 포트 8080 단일 진입점, JWT 인증 처리 | 클라이언트가 각 서비스 직접 호출 안 하는 이유 |

> **CTO 검토 반영 — Kafka 흐름 주의**: enrollment→payment는 **WebClient(동기)**, payment→enrollment, enrollment→recommend만 **Kafka(비동기)**

#### Docker (슬라이드 11)
- 기동 의존 순서: `MariaDB / Kafka → Eureka → Auth Server → 서비스들 → recommend`

#### 서비스 간 통신 구분 (슬라이드 13)
- **동기 (WebClient)**: 즉시 응답 필요 (enrollment → payment 결제 요청)
- **비동기 (Kafka)**: 결과를 기다리지 않아도 되는 경우 (결제 완료 후 상태 변경, 추천 갱신)

#### 미리 답할 예상 질문 (슬라이드 17)
- "왜 공유 DB를 쓰나요?" → 실습 환경 제약(단일 MariaDB 컨테이너). 운영 시 DB per Service로 분리 예정
- "Python 서비스는 Eureka 연동을 어떻게 했나요?" → `py-eureka-client` 라이브러리 사용 (Java Spring Cloud와 동일 레지스트리 공유)

### 5-2. 아키텍처 설계서 (팀 공동, #1 주도)

**형식**: Markdown 문서 (`PLAN/아키텍처_설계서.md`)

**포함할 내용:**

**① 서비스 구성도 (다이어그램)**
- 7개 서비스 박스 + 화살표로 통신 방향 표시
- Gateway → Eureka → 서비스들 계층 구조

**② 각 서비스 역할 정의**

| 서비스 | 포트 | 역할 |
|--------|------|------|
| api-gateway | 8080 | 클라이언트 단일 진입점, JWT 인증 |
| eureka-server | 8761 | 서비스 등록·검색 (Service Discovery) |
| auth-server | 9000 | OAuth2 토큰 발급 |
| user-service | 8081 | 회원·공급사 관리 |
| course-service | 8082 | 분양 공고 조회·공공 API 연동 |
| enrollment-service | 8083 | 청약 신청·접수 처리 |
| payment-service | 8084 | 접수 수수료 처리 |
| recommend-service | 8085 | 개인화 추천 (Python FastAPI) |

**③ 서비스 간 통신 흐름**

```
[청약 신청 플로우]
사용자 → Gateway(8080) → enrollment-service
  └─ WebClient(동기) → payment-service [결제 요청]
  └─ Kafka: payment.completed → enrollment-service [PENDING→ACTIVE]
  └─ Kafka: enrollment.completed → recommend-service [추천 갱신]

[분양 공고 조회 플로우]
사용자 → Gateway(8080) → course-service [공공 API 데이터 반환]

[AI 추천 플로우]
사용자 → Gateway(8080) → recommend-service → course-service [공고 데이터 조회]
```

**④ ERD (DB 스키마)**

| 테이블 | 담당 | 주요 컬럼 |
|--------|------|---------|
| users | #1 (PM) | id, name, email, role(STUDENT/INSTRUCTOR) |
| courses | **#2 (쏘피)** | id, title, price, category(enum), instructor_id(FK→users) |
| enrollments | #3 | id, user_id(FK), course_id(FK), status(PENDING/ACTIVE) |
| payments | #3 | id, enrollment_id(FK), amount, status |

**⑥ 설계 결정 사항 & 트레이드오프**
- **공유 DB**: 실습 환경 제약으로 schema-per-service 적용 (운영 시 DB per Service로 분리 예정)
- **Java + Python 혼용**: 추천 서비스는 ML 라이브러리 활용 위해 Python FastAPI 선택, 동일 Eureka 레지스트리 공유
- **동기/비동기 혼용**: 즉시 응답 필요 구간(결제 요청)은 WebClient, 결과를 기다리지 않아도 되는 구간(상태변경·추천갱신)은 Kafka
