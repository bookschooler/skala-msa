## 🎯 우리 팀 아이디어

# HomeOne — B2B2C 분양 정보 플랫폼

### 📢 발표 첫 슬라이드 문구 (이대로 씁니다)

> **여러 건설사·시행사의 공공·민간 분양 정보를 한 곳에 모아,
> 청약 신청자에게는 지역·예산·경쟁률 조건에 맞는 분양 단지를 추천하고,
> 공급사에게는 접수 현황을 제공하는 B2B2C 분양 정보 플랫폼.**
>
> **인기 분양 접수 시점의 트래픽 급증에도 조회·추천이 중단되지 않도록
> 서비스를 분리하고 이벤트 기반으로 연계했습니다.**

**두 문장으로 쪼갠 이유:** 1문장 = **What**(가치와 3층 구조), 2문장 = **How**(아키텍처).
첫 슬라이드에서 이 둘이 한 문장에 섞이면 청중 머리에 아무것도 안 남습니다.

### 첫 슬라이드 하단에 반드시 병기할 한 줄

> **1차 릴리스 범위 (Sprint 1–2):** 신청자 웹 4화면 + 공급사 파트너 API + 추천 서비스
> **Sprint 3 백로그:** 공급사 관리 콘솔 · 운영자 승인 워크플로 · 마감 일괄 처리

제품 비전과 스프린트 범위를 분리하는 것은 애자일에서 **정확한 실천**이지 변명이 아닙니다.

### ⚠️ 초안에서 무엇을 고쳤고 왜 고쳤는가 (팀이 알고 있어야 합니다)

| 초안 | 수정 | 이유 |
|---|---|---|
| 건설사·시행사의 | **여러** 건설사·시행사의 | 아그리게이터 성격 명시 (단일 건설사 사이트가 아님) |
| *(없음)* | **공급사에게는 접수 현황을 제공** | 🔴 **초안에는 B의 이득이 없었습니다.** B가 "정보를 제공당하는 쪽"으로만 나와서 **"이게 왜 B2B2C죠?"를 정확히 맞습니다** |
| 조건 기반 맞춤 | **지역·예산·경쟁률 조건에 맞는** | "무슨 조건이요?" 질문을 **슬라이드가 미리 답합니다** |
| 공고 | **분양 단지** | 공고(공급 공고문)는 접수기간·자격·일정을 포함하는 문서 → 전부 Won't. 문구와 Won't가 어긋나면 지적당합니다 |
| 청약 **신청** | **접수** | "신청"은 청약홈의 법정 신청을 연상 → "1순위 자격 검증은요?"가 옵니다. 그건 Won't |
| **대규모 트래픽에 대응** | **트래픽 급증에도 조회·추천이 중단되지 않도록** | 🔴 **못 지키는 약속이었습니다.** 아래 참조 |

> 🚨 **"대규모 트래픽에 대응"을 왜 지웠는가**
> 이렇게 쓰면 심사위원 머릿속에 자동으로 **부하테스트 결과 슬라이드**가 그려집니다.
> 그게 안 나오면 "못 한 것"이 아니라 **"약속을 안 지킨 것"**이 됩니다. 인상이 완전히 다릅니다.
>
> **약속의 크기는 스스로 정하는 것입니다.** "대응"이라는 모호한 큰 말을
> **"중단되지 않도록"이라는 검증 가능한 작은 말**로 바꿨을 뿐인데,
> 우리가 실제로 시연하는 것(장애 격리 + Kafka 버퍼링)과 **약속이 1:1로 맞습니다.**
>
> 약해 보이지 않습니다. **평가위원은 "대응하겠습니다"를 수백 번 봤고 아무 감흥이 없습니다.**
> 구체적인 작은 말이 모호한 큰 말을 항상 이깁니다.

> ⚠️ **실제 「청약홈」·한국부동산원을 사칭하지 마세요.** 우리는 정부 시스템이 아니라
> **정보를 모아 보여주는 민간 아그리게이터**입니다. 단지명·건설사명·신청자 이름은
> 전부 **가상**으로 만듭니다. 실제 브랜드명(자이·래미안·힐스테이트)도 쓰지 않습니다.

### 🏛️ B2B2C 3층 구조 — 양방향 가치 순환

```
  시행사·건설사 ──[공고 등록: 파트너 API]──▶ HomeOne ──[조회·추천]──▶ 청약 신청자
   (B: 공급)                                (플랫폼)                    (C: 수요)
        ▲                                                                    │
        └──────[접수 현황·경쟁률]──── enrollment (Kafka 이벤트) ◀──[청약 접수]──┘
```

**이 그림을 아키텍처 구성도(PM 담당)에 화살표로 반드시 그리세요.**
아래쪽 되돌아오는 화살표가 **B2B2C를 증명하는 유일한 선**입니다.

| 층 | 누구 | 무엇을 얻나 | 우리 시스템에서 |
|---|---|---|---|
| **B** | 시행사·건설사 | **채널 접근** + 접수 데이터 가시성 | 파트너 API로 공고 등록 / 경쟁률로 접수 현황 확인 |
| **B** | HomeOne (우리) | 중개 + 청약금 에스크로 | 조회·접수·추천 서비스 운영 |
| **C** | 청약 신청자 | 흩어진 분양 정보를 한 곳에서 + 맞춤 추천 | 웹 4화면 |

## 🖥️ 화면은 4개로 고정합니다 — B층은 API로 증명

> 🔒 **이건 협상 대상이 아닙니다. 보드에 명문화하세요.**
> 화면 4개: **로그인 / 단지 목록 / 단지 상세 / 청약 접수·결과**

### "B2B2C인데 공급사 화면이 없네요?" — 이렇게 답합니다

> **"B2B2C의 정의는 세 층이 각자 화면을 갖는 것이 아니라, 플랫폼이 B의 공급을 C의 수요에
> 중개하고 양쪽에서 가치를 얻는 것입니다. 데이터 흐름이 3층이면 B2B2C이고, 화면 수와는 무관합니다."**

그리고 실무 근거를 덧붙입니다.

> **"아그리게이터 플랫폼의 초기 MVP에는 공급자 포털이 없습니다.**
> 공급사는 엑셀이나 이메일로 공고를 넘기고 운영자가 대신 등록합니다.
> 부동산·채용·숙박 어느 도메인이든 초기 단계는 다 이렇습니다.
> 공급자 셀프서비스 포털은 공급사 수가 늘어 **수기 등록이 병목이 된 다음**에 만듭니다."

> 💡 **"1일차부터 공급자 포털을 만들었습니다"가 오히려 실무 감각이 없는 답입니다.**

### ② AI 솔루션 (발표 2번 항목)

> **조건 기반 맞춤 단지 추천.**
> 신청자의 과거 접수 이력에서 **지역·예산 성향**을 뽑아,
> 같은 조건에서 **아직 접수하지 않았고 경쟁률이 낮은** 단지를 5곳 골라 **이유와 함께** 제시한다.

원본 템플릿의 추천은 `enrollment_count DESC`(인기순)입니다.
청약에서는 **인기 = 당첨 확률 낮음**이므로 **정렬을 `ASC`로 뒤집습니다.**

#### 추천 조건 — 총 5개가 상한입니다

| # | 조건 | 우선순위 | 담당 | 비용 |
|---|---|---|---|---|
| 1 | 같은 **지역**(category) | 기본 | A | 0 (원본) |
| 2 | **미접수** 단지만 | 기본 | A | 0 (원본) |
| 3 | **경쟁률 ASC** (접수건수 ÷ 공급세대수) | 기본 | A | 정렬 1줄 |
| 4 | **예산** — 과거 접수 단지 분양가 평균 × 1.2 이하 | **P1** | A | **20분** |
| 5 | **공급유형** — 공공 접수 이력자에게 공공 우선 | P2 | A | 10분 |

> 🔴 **조건 1개의 실제 비용은 "규칙 1줄"이 아닙니다.**
> 규칙 + **그 조건이 작동하는 게 보이도록 시드 세팅** + 화면 표시 + 디버깅 = **조건당 20~30분.**
> Sprint2 150분 중 추천에 쓸 수 있는 건 최대 50분이므로 **추가 2개가 물리적 상한**입니다.

> 🔴 **예산 조건의 함정 — 반드시 처리하세요.**
> 접수 이력이 0건인 사용자는 평균이 null → 전체가 필터링되어 **추천 0건**.
> 반드시 **`이력 없음 → 예산 조건 미적용`** 분기를 넣으세요.
> **증상: 새 계정으로 시연하다가 추천 화면이 텅 빔.** 에러가 안 나서 원인을 못 찾습니다.
> → 추가 안전장치: **발표 데모 계정을 접수 이력 2건 있는 계정으로 고정**하고 대본에 계정명을 적어두세요.

#### 🏅 "무슨 조건이요?"의 진짜 방어는 조건 개수가 아니라 화면입니다

### 차단 이슈 — 강사에게 확인할 것

| # | 확인할 것 | 왜 |
|---|---|---|
| 1 | **소스 패키지 + build용 `docker-compose.yml`** 언제 받나 | 지금 폴더엔 이미지 tar와 PDF뿐. `course-service/` 등 소스 디렉터리가 **전무**합니다. 이거 없으면 조별 실습 시작 불가 |
| 2 | `init-db/` 폴더는 어디에 | compose가 `./init-db`를 마운트하는데 없으면 Docker가 **빈 폴더를 자동 생성**해 조용히 마운트합니다. **에러 없이 데이터 0건** |
| 3 | 로그인 API가 정확히 무엇인가 | 가이드2는 `/api/users/login`, 가이드3 설계표엔 login이 없음, auth-server는 `/oauth2/token`. **문서 3종이 서로 다른 말을 합니다** |
| 4 | 게이트웨이(8080) 경유 시 토큰이 필요한가 | compose의 issuer 설정이 서비스마다 다릅니다 (`localhost:8080` vs `auth-server:9000`). 한쪽은 반드시 검증 실패 → **401이 나와도 자책하지 말고 개별 포트로 우회** |
| 5 | `courses` 테이블에 `enrollment_count` 컬럼이 실제로 있나 | 없으면 경쟁률 스토리 전체를 다시 짜야 합니다 |
| 6 | `vue-frontend`는 컨테이너인가 `npm run dev`인가 | 문서마다 다릅니다. Node 버전도 확인 |
| 7 | Kafka Consumer의 `FAIL_ON_UNKNOWN_PROPERTIES` 설정값 | `true`면 payload에 필드 추가하는 순간 **컨슈머가 조용히 계속 죽습니다** |

### 🎓 교수님 지시("PO / 스크럼마스터 / 개발로 나누라")를 이렇게 만족시킵니다

> **작은 팀에서 겸직은 정상적인 형태**입니다.

**교수님께 이렇게 답하면 됩니다:**
> "PO와 SM을 명시적으로 두되 겸직으로 운영했습니다. 대신 **역할별 실물 산출물**을 남겼습니다.

역할을 "말"이 아니라 **"제출물"**로 증명하는 것이 핵심입니다.

> 초심자 팀에서 4명 전원이 코딩에 몰입하면 통합과 발표 준비가 **100% 펑크**납니다.

### ⚠️ 이 역할 배정에서 새로 생긴 위험 3가지 (실제 코드 확인 결과)

#### ① 🔴 "정렬 ASC로 뒤집기"는 1곳이 아니라 **2곳**이고, **주인이 서로 다릅니다**

| 경로 | 파일 | 소유 |
|---|---|---|

## E. 병렬 작업이 깨지지 않게 하는 규칙 9가지

### 1. Contract First — 명세 없이 코딩 시작 금지
**Day1 14:50까지 API 응답 JSON 예시를 "실물"로 확정합니다.**
스키마 표가 아니라 **복사해서 바로 쓸 수 있는 JSON 덩어리**로요.
```
GET /api/courses  →  [{ "id":1, "title":"한빛마을 3단지 84A", "category":"SEOUL",
                        "price":98000, "instructorId":2, "enrollmentCount":1240 }]
```
이 JSON을 `public/mock/courses.json`에 저장하면 PM은 백엔드 없이 15:00부터 화면을 만듭니다.

### 2. 1인 1디렉터리 — 소유자 외 편집 금지
A=`course-service/` `recommend-service/` / B=`init-db/` `docker-compose.yml` /
C=`enrollment-service/` `payment-service/` / D=`vue-frontend/`

### 3. 프론트는 기다리지 않는다
명세대로 먼저 붙이고 404는 그대로 둡니다. **단, 목업으로 끝내면 안 됩니다** (작년 실패 사례 ①).
Day2 오전에 반드시 실서버로 전환합니다.

### 4. git — `main` 직접 push 금지
브랜치명 `feature/<이름>-<기능>`. **머지는 B(SM)를 통해서만.** 통합은 하루 2회.

### 5. 🔒 `docker compose down -v` 는 PM만, 하루 3회만

`down -v`를 하면 **볼륨이 날아가고 전 서비스가 다시 뜰 때까지 3~5분간 아무도 아무것도 테스트할 수 없습니다.**
각자 마음대로 하면 하루 종일 **"어? 방금 만든 데이터가 사라졌는데요?"** 가 반복됩니다.

| 시각 | 목적 |
|---|---|
| Day1 16:35 | Sprint1 시작 (시드 반영) |
| Day2 09:10 | Sprint1 잔여 시작 |
| Day2 13:00 | 컬럼 추가 반영 |

그 외 시간에 데이터가 필요하면 `down -v` 대신 컨테이너에 직접 넣습니다.
```bash
docker exec -i lecturedb mariadb -umanager -pSqlDba-1 lecture_db \
  -e "INSERT INTO courses (title, category, price, instructor_id, enrollment_count) VALUES ('임시단지 84A','SEOUL',50000,2,10);"
```

### 6. 🔒 필드 이름 변경 금지, **추가만** 허용 ← 가장 중요한 규칙

`courses.price → enrollment → payments.amount` 가 **한 줄로 엮여** 있습니다.
하나만 바꿔도 서비스 3개가 동시에 깨지는데, **에러가 안 나고 값이 null로 조용히 흐릅니다.**

| 하면 되는 것 | 절대 금지 |
|---|---|
| 시드 데이터 **값** 변경 | DB **컬럼명** 변경 |
| 화면 **문구** 변경 | DTO **필드명** 변경 |
| Swagger `@Operation(summary)` 변경 | `/internal/**` **경로** 변경 |
| 새 필드 **추가** (Sprint2, A 단독) | 테이블·엔티티 **이름** 변경 |

**"코드는 courses, 화면은 단지."** 이 문장을 벽에 붙이세요.

### 7. 🔒 Kafka는 **Consumer 먼저, Producer 나중**

payload에 필드를 추가할 때 순서를 지킵니다.
1. **Consumer(enrollment-service)** 먼저 배포 — 새 필드를 받을 준비
2. 그다음 **Producer(payment-service)** 배포

반대로 하면 역직렬화 실패로 **이벤트를 통째로 잃고, 화면은 영원히 PENDING**입니다.

### 8. 🔒 재시작 후 90초는 무조건 기다린다 — 시간 낭비 1위

서비스를 재시작하면 Gateway가 라우팅을 다시 잡는 데 **30~90초** 걸립니다.
초심자는 5초 만에 새로고침해서 503을 보고 **"내 코드가 틀렸다"며 멀쩡한 코드를 고치기 시작합니다.**
그러다 **진짜로 망가뜨립니다.**

- 재시작 후 **90초 대기.** 그 사이엔 `docker compose logs -f <서비스>` 를 봅니다
- http://localhost:8761 (Eureka) 을 항상 탭에 띄워두고 **UP 확인 후** 호출
- **503이 나오면 코드를 고치기 전에 Eureka부터 봅니다**

### 9. 🔒 재빌드는 한 번에 한 명만, 서비스 1개만

```bash
# ⭕ 서비스 1개만, 캐시 사용 (2~4분)
docker compose -f docker-compose.local.yml up -d --build course-service

# ⭕ 파이썬(recommend)은 restart 만으로 충분
docker compose -f docker-compose.local.yml restart recommend-service

# ⭕ 프론트가 Vite dev 라면 빌드 불필요 (HMR 즉시 반영)

# ❌ Sprint 중 절대 금지 (15~25분). 통합 때 1회만.
docker compose build --no-cache
```

**Java 서비스 재빌드는 2~4분. 4명이 각자 돌리면 노트북이 죽습니다.**
